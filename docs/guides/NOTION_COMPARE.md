> **문서 용도**: Notion DB와 사이트 데이터를 대조하는 프로그램(`scripts/notion-compare/`)과 대조표 운영 절차. 에이전트와 사용자가 함께 본다. 공개 페이지에는 쓰지 않는다.

# Notion 데이터 대조표

## 무엇을 하나

- Notion DB(읽기 전용)와 사이트 데이터 파일을 항목별로 비교해 다른 곳을 모은다.
- 결과는 비공개 대조표 페이지로 보고, 항목마다 어느 쪽에 맞출지 고른다.
- 고른 결과를 Claude가 읽어 사이트 파일·Notion 원본을 고친다.
- 자동 예약은 없다. 사용자가 요청할 때 실행한다(사용자 결정).

## 실행

```bash
npm run compare:notion
```

```bash
npm run compare:notion -- hsr
```

```bash
npm run compare:notion -- ww
```

- 필요한 것: `.env.local`의 `NOTION_TOKEN`, 각 DB가 연동 계정(Rira-Game-Hub-DB)에 공유돼 있어야 한다.
- 허브를 골라 실행하면 그 허브만 새로 비교하고, 나머지 허브는 마지막 결과(`items.json`)를 그대로 둔다. 그래서 대조표를 다시 게시해도 다른 허브가 빠지지 않는다.
- 결과: `.tmp/notion-compare/items.json`(항목 목록), `.tmp/notion-compare/review.html`(대조표 페이지). 둘 다 Git 제외다.
- Notion 요청 속도 제한 때문에 페이지마다 잠깐 쉰다. HSR 전체는 몇 분 걸린다.

## 대조표 게시

- 대조표 주소: https://claude.ai/artifact/QzebC8KKRnVMtCoYz2pybe ("RIRA 데이터 대조표", 비공개, 소유자만 열 수 있음)
- 한꺼번에 고르기: 필터(게임·DB·유형·상태·검색)로 보이는 항목 전체를 한 번에 기준·사이트 기준·차이 무시·보류로 저장하거나 선택을 지울 수 있다(확인 후 저장). 애니모처럼 한 기준으로 맞출 때는 게임을 고르고 "공식 도감 기준"을 한 번 누르면 된다. 묶음(대상 하나)마다 같은 버튼도 있다.
- 갱신할 때는 `review.html`을 같은 주소로 다시 게시한다. 선택·메모는 아티팩트 저장소(`decisions` 모음)에 있어서 다시 게시해도 남는다.
- 선택 문서 하나: `choice`(notion·site·both·memo·ignore·hold), `note`, `hub`, `db`, `target`, `cat`, `label`, `hash`, `updatedAt`.

## 항목 id와 상태

- 항목 id는 위치(허브·DB·대상·분류·라벨)로 정한다. 문구가 바뀌어도 같은 차이면 선택이 이어진다.
- `hash`는 비교한 문구로 정한다. 선택할 때의 `hash`와 지금 항목의 `hash`가 다르면 "선택 후 내용 바뀜"으로 표시한다. 다시 확인이 필요하다는 뜻이다.
- 선택은 있는데 지금 대조에 나오지 않는 항목은 "해결됨"으로 모인다. 수정이 반영됐거나 비교 방식이 바뀐 경우다.
- HSR 항목의 `legacyId`는 2026-11-11 수동 대조 때의 id다. 그때 저장한 선택을 이어 쓰기 위해 둔다.

## "대조표대로 수정" 절차

1. 아티팩트 저장소의 `decisions`를 모두 읽고, 최신 `items.json`(먼저 `compare:notion` 실행)과 짝짓는다. 짝은 `id` 또는 `legacyId`로 찾는다.
2. 고칠 대상만 고른다.
   - `site`(사이트 기준): Notion을 사이트 값으로 고친다.
   - `notion`(Notion 기준): 사이트 파일을 Notion 값으로 고친다.
   - `both`, `memo`: 메모에 적힌 대로 고친다. 메모가 비었거나 뜻이 불분명하면 고치지 않고 사용자에게 묻는다.
   - `ignore`, `hold`, 해결됨, "선택 후 내용 바뀜"은 고치지 않는다(내용 바뀜은 사용자에게 다시 확인).
3. Notion 수정은 `AGENTS.md`의 "Notion 원본 함께 수정" 절차를 따른다. 한 블록·한 속성에만 있는 문장만 바꾸고, 바꾼 뒤 다시 읽어 확인한다.
4. 사이트 파일 수정 뒤에는 필수 검증(타입 검사, 빌드, diff)을 거쳐 commit·push한다.
5. `compare:notion`을 다시 실행해 고친 항목이 "해결됨"으로 옮겨 갔는지 확인하고, 대조표를 다시 게시한다.

## 허브 추가

- `scripts/notion-compare/hubs/<허브>/index.js`에 허브 객체(`id`, `name`, `compare()`)를 만들고 `scripts/notion-compare/index.js`의 `HUBS`에 넣는다.
- `compare()`는 Notion DB를 읽고(`lib/notion.js`), 사이트 TypeScript 데이터를 불러와(`lib/site-data.js`) 차이마다 `list.add({ db, target, cat, label?, notion?, site?, text?, kind?, hint? })`를 부른다.
- 문구 비교는 `lib/text.js`의 `textKind`를 쓴다. 띄어쓰기만 다르면 차이로 세지 않는다.
- 공통 규칙: 어느 쪽이 맞는지 추정해 값을 채우지 않는다. 데이터만 보고 알 수 있는 경우에만 `hint`(예: "반올림 차이", "Notion 오타 의심")를 단다.

## 명조 비교 범위

명조는 Notion → `common-hub/data/notion-data.json`(동기화) → 화면에서 `ww-hub` 로컬 파일과 합치는 구조다(`common-hub/data/dataManager.ts`). 대부분 Notion 값이 우선이고, 로컬 파일이 우선인 칸(스킬이 있는 로컬 캐릭터의 간단 정보·소속·성우 등)과 Notion이 비었을 때 쓰는 칸이 있다. 그래서 세 가지를 본다.

- **동기화 대기:** 지금 Notion 내용과 마지막 동기화 결과(`notion-data.json`)가 다른 곳. 동기화 스크립트의 해석 함수(`fetchFromDB`, `fetchWwGuidesFromDB`)를 그대로 쓴다. 대상: 무기, 캐릭터, 아이템, 에코, 공략.
- **사이트가 로컬 값 표시:** Notion에 값이 있는데 화면에는 로컬 파일 값이 나오는 곳. 화면 데이터(합친 결과)와, 로컬 목록을 비우고 다시 합친 "Notion만 썼을 때 결과"를 비교한다. 대상: 캐릭터 이름·속성·무기 종류·희귀도·출시 버전·소속·간단 정보·성우·역할. 번역 키는 한국어 문장으로 풀고, 국기 이모지와 줄바꿈 차이는 무시한다.
- **로컬 파일만 다름:** 화면은 Notion 값을 보여 주지만 로컬 파일 값이 다른 곳. 로컬 파일을 직접 읽는 다른 기능에 낡은 값이 남을 수 있다. 대상: 캐릭터 속성·무기 종류·희귀도·출시 버전, 무기 종류·희귀도·출시 버전.
- 로컬에만 있는 항목은 DB마다 한 줄로 묶는다(예: Notion에 없는 에코 목록).
- 화면 데이터는 Vite SSR로 불러온다(`lib/vite-data.js`). 앱과 같은 방식이라 `import.meta.glob` 같은 Vite 기능도 그대로 동작한다.

## 이환(NTE) 비교 범위

이환 캐릭터·아크·아이템은 Notion → `notion-data.json`에서 오고, `nte-hub` 로컬 목록은 거의 비어 있어 화면이 곧 Notion 값이다. 공략은 동기화 때 마크다운 본문 전체가 `common-hub/data/guideArticles.json`에 저장된다(`scripts/lib/sync-nte-guides.js`).

- **동기화 대기:** 캐릭터·아크·아이템. 동기화가 저장 전에 붙이는 기본값(아이템 `type: '아이템'`, 아크 `type: '결합'`, 캐릭터 `type: '캐릭터'`)을 똑같이 붙여 비교한다.
- **공략:** Notion 공략 본문과 저장된 공략 본문을 줄 단위로 비교해 바뀐 부분만 보인다. 라벨은 가장 가까운 제목(`#`)과 그 아래 몇 번째 차이인지다. 제목과 검수일(`reviewedAt` = Notion 마지막 수정일)도 본다. 로컬 분석 블록(`nte-hub/data/guideAnalysis.json`)은 비교하지 않는다.
- **로컬 파일만 다름:** `nte-hub` 로컬 캐릭터·아크가 Notion과 다른 칸. Notion 빈 칸이 로컬 값을 덮어 화면에 안 보이는 경우도 여기에 나온다. 줄바꿈만 다른 칸은 빼고 본다.

## 애니모 비교 범위

애니모는 Notion DB가 없다. 원본이 공식 도감(wiki.aniimo.com)이라 대조표에서는 왼쪽이 "공식 도감"으로 표시된다. 공식 페이지를 읽기만 하고 파일은 쓰지 않는다(페이지마다 잠깐 쉰다).

- 기존 지역(`aniimo-hub/data/aniimo.json`)은 `scripts/fetch-aniimo-data.js`의 해석기로, 웨이브 군도(`wave-archipelago.json`)는 `scripts/lib/aniimo-wave-parser.js`로 읽는다. 저장할 때 쓴 해석기를 그대로 써야 두 지역의 이름 규칙 차이(바위·땅 등)가 차이로 잡히지 않는다.
- 공식 도감이 기준이라 구역(그림, 속성, 역할, 능력치, 설명, 출현 지역, 홈 능력, 탐사 스킬, 특성, 전투 스킬, 고유 스킬, 진화 단계, 공명 단계)을 통째로 묶지 않고 세부 항목마다 따로 고르게 한다. 분류는 "형태 · 구역", 라벨은 세부 항목이다.
  - 스킬: 스킬 하나의 이름·설명·종류·에너지·위력(스킬은 이름으로 짝짓고, 한쪽에만 있으면 스킬 전체 한 건).
  - 능력치: 능력치 하나. 공명 단계: 단계 하나의 조건·재료. 진화 단계: 몇 번째 단계. 홈 능력: 종류 하나.
  - 속성·역할·출현 지역: 한쪽에만 있는 값 하나씩(순서만 다르면 "순서" 한 건). 형태 목록: 형태 하나.
- 형태 목록, 공식 목록에만 있는 애니모(새 항목), 사이트에만 있는 애니모도 보인다.
- "공식 도감 기준"으로 고칠 때는 `docs/guides/ANIIMO_DATA.md`의 공식 데이터 갱신 절차와 `AGENTS.md`의 Aniimo 규칙을 따른다. 기존 항목·이미지·URL을 덮어쓰지 않고, 공식 자료에 없는 값은 추정해 채우지 않는다.
- 예전 `fetch-aniimo-data.js`는 직접 실행할 때만 수집한다. 가져와 쓰면 해석기만 쓰고 아무것도 받거나 쓰지 않는다.

## HSR 비교 범위

- 캐릭터: 기본 정보, 언어별 표기, 성우, 간단 정보, 성장 스탯, 승급·행적 재료, 스킬·추가 능력·성혼 이름과 문구, 속성 보너스. "(AS)" 페이지는 `asBuffData`와 비교한다.
- 광추: 이름, 운명의 길, 성급, 출시 버전, 효과 이름·문구(사이트가 1중첩 수치만 적은 경우 구분), 성장 스탯, 돌파 재료, 스토리.
- 유물·장신구: 종류, 출시 버전(유물만), 2·4세트 효과, 파츠 이름.
- 공략: 동기화 스크립트의 비교 기준(추천 장비, 주옵션, 부옵션, 목표 스탯, 스킬 우선순위, 추천 파티). 공략 본문 문단은 비교하지 않는다.
- 추천 파티: 파티 구성과 대체 캐릭터.
