# 3인 독립 품질 평가 실행 기준

프로토콜 버전: 1.0 · 작성일: 2026-10-15 · 적용: 공개된 HSR·WW·NTE·Aniimo와 공통 기능.

## 목적과 실행 방식

한 명의 종합 인상평으로 끝내지 않는다. 성능 엔지니어, 보안 엔지니어, 디자인·UX 엔지니어가 같은 버전을 **서로 독립적으로** 검사하고 각자 보고서를 작성한다. 가능하면 별도 에이전트 3개를 사용한다. 실제 사람 3명이 참여한 것으로 표현하지 않는다.

기준 문서는 사용자 요청 → AGENTS.md → 해당 분야 정책 순서로 적용한다. 디자인 정책은 [DESIGN.md](../../DESIGN.md), 성능 정책과 용량 예산은 [PERFORMANCE.md](PERFORMANCE.md)가 원본이다. 이 문서는 정책을 새로 정의하는 대신 실행·증거·판정 방법을 정한다.

사용자 선택: **자동 예약 없음.** 필요할 때 요청으로 실행하며 자동 감시·정기 실행 중이라고 보고하지 않는다. 매 작업은 변경 범위에 맞는 3인 검토, 전체 재평가는 사용자가 요청할 때 아래 고정 목록으로 실행한다. 접근 불가능한 항목은 범위를 줄여 숨기지 않고 미검증으로 남긴다.

## 재사용 요청문

> 3인 품질 평가 실행. docs/guides/THREE_ENGINEER_REVIEW.md 기준으로 성능·보안·디자인 담당을 별도 에이전트로 나눠 같은 commit을 독립 평가하고, 실제 측정·화면·권한 검증 증거와 미검증 항목을 각각 보고해. 우선 평가는 읽기 전용으로 하고 자동 수정·Notion 동기화·운영 데이터 변경은 하지 마. 마지막에 우선순위를 합쳐 줘.

기능 구현 요청에 포함된 검토는 해당 구현 범위에서 수행하되, 발견된 별개 기능·권한·데이터를 임의로 변경하지 않는다.

## 1. 사전 조건 고정

1. git status, HEAD, branch, 작업 diff를 확인한다. 기존 사용자 변경·secret은 보존한다.
2. 평가 대상 commit과 실제 배포 commit이 같은지 확인한다. 배포 버전 확인 불가 시 운영 버전은 미확인이다.
3. 일시·시간대, URL·query, 언어, 브라우저/OS/도구 버전, viewport, 로그인·광고·쿠키 동의 상태를 기록한다.
4. 기본은 한국어·로그아웃이다. 인증·번역 변경은 해당 상태를 추가한다. 비밀정보·개인정보가 담긴 URL이나 화면은 공개 보고서에 저장하지 않는다.
5. 전체 평가인지 변경 범위 평가인지 먼저 선언한다. 코드·데이터 변경이면 AGENTS.md에 따른 타입/테스트/빌드/diff 검증도 수행한다. 문서만 바꾸는 작업은 문서·링크·diff 검토로 검증할 수 있다.
6. Notion 동기화는 명시 요청 없으면 금지한다. package.json의 lifecycle을 먼저 확인한다. Windows spawn EPERM은 환경 실패로 기록하며 허용된 외부 실행 성공 전에는 빌드 통과가 아니다.

## 2. 독립 검사와 교차 검토

1. 세 담당에게 같은 commit·범위·환경·원본 기준을 전달한다. 각자는 다른 담당 결론을 보기 전에 검사하고 1차 판정을 고정한다.
2. 각 담당은 [보고서 양식](../templates/three-engineer-review.md)의 독립 보고서를 별도 파일로 작성한다. 단순 체크리스트 복사나 역할 이름만 바꾼 종합평은 금지한다.
3. 성능 → 디자인: 성능 개선이 콘텐츠·광고·이미지를 숨겨 점수만 높이지 않았는지 검토한다.
4. 보안 → 성능: 로깅·인증·CSP·캐시 완화로 성능을 높이지 않았는지 검토한다.
5. 디자인 → 보안: 로그인·오류·관리자 UI가 민감정보 노출이나 잘못된 권한 인식을 만들지 않는지 검토한다.
6. 교차 검토 후 이견을 기록한다. 주 담당은 독립 검토자의 실패를 임의로 통과로 바꾸지 않는다. 에이전트 사용 불가 시 역할별 분리 검토라고 밝히고 독립성 한계를 남긴다.
7. 세 결과를 합산 점수로 평균 내지 않는다. P0/P1 실패 또는 핵심 미검증이 있으면 전체 통과를 선언하지 않는다.

## 3. 고정 화면과 여정

전체 평가 시 아래 경로를 사이트맵·router에서 먼저 확인한다. 삭제/변경된 경로는 실패 또는 정책상 의도된 폐쇄로 구분한다. 대체 표본은 이유·일자를 기록하고 이전과 비교할 수 있게 남긴다.

- 공통: `/`, `/about`, `/privacy`, `/contact`. 가이드 목록은 아래 각 허브 경로를 사용한다.
- HSR: `/gallery/hsr`, `/gallery/hsr/character/feixiao`, 같은 경로의 `/guide`, `/gallery/hsr/guides`.
- WW: `/gallery/ww`, `/gallery/ww/character/baizhi`, 같은 경로의 `/guide`, `/gallery/ww/guides`.
- NTE: `/gallery/nte`, `/gallery/nte/character/감정사`, `/gallery/nte/guides/감정사-build-guide`, `/gallery/nte/guides/esper-cycle-combat-guide`.
- Aniimo: `/gallery/aniimo`, `/gallery/aniimo/characters`, `/gallery/aniimo/character/탄멍멍`, `/gallery/aniimo/type-chart`, `/gallery/aniimo/guides/evolution-and-forms-guide`.
- 각 허브의 현재 티어표·파티 추천은 router와 실제 사이드바 링크에서 확인해 보고서에 URL을 고정한다. 존재하지 않는 기능을 억지로 테스트하지 않는다.
- 변경 화면 및 최근 이미지/데이터가 바뀐 캐릭터를 추가 표본으로 넣는다. GF2 등 미공개 화면은 공개 합격 범위에 넣지 않는다.

기본 시각 조건: 모바일 390×844, 데스크톱 1440×900. 전체 디자인 평가에는 320×844 좁은 화면, 768×1024 중간 화면, 긴 이름·영문/일문, 200% 확대, 키보드 검사를 추가한다. PSI는 자체 기기 에뮬레이션을 사용하므로 실제 설정을 그대로 기록하고 이 viewport와 같다고 하지 않는다.

공통 사용자 여정:

1. URL 직접 진입 → 새로고침 → 초기 HTML에서 앱으로 전환.
2. 홈 → 허브 → 목록 필터/검색 → 캐릭터 상세 → 세팅/분석 → 뒤로가기.
3. 모바일 메뉴, sticky navigation, 이미지·스킨 전환, 추천 장비 링크.
4. 통합 검색 버튼·Ctrl/Cmd+K·닫기·Esc·포커스 복귀.
5. 긴 스크롤, 로딩·빈 목록·이미지 오류·요청 실패·재시도. 안전한 로컬/테스트 환경에서만 실패를 주입한다.

## 4. 성능 엔지니어

- 타입·회귀 테스트·현재 commit으로 생성된 production build의 SEO/성능 예산을 확인한다. 이미 생성된 dist를 쓰면 생성 버전부터 확인한다.
- 콜드 직접 진입, 웜 재진입, SPA 목록→상세 이동을 구분한다. 브라우저 HTTP 캐시 초기화를 확인하지 못하면 '콜드 미확인'으로 적는다.
- 전체 실측은 홈 + 각 허브 메인/목록·상세·세팅/분석의 대표 경로에서 모바일·데스크톱별 독립 3회 수행한다. 상태·도구가 다른 결과끼리 중앙값을 만들지 않는다. 불가능한 조합은 미측정 사유를 남긴다.
- 매 실행 FCP/LCP/CLS/TBT, 측정 시각, 리포트 원본, 가능하면 전송량·요청 수·긴 작업·폰트/이미지/동적 chunk·서드파티 비용을 보관한다. 독립 실행별 원자료를 지우고 중앙값만 남기지 않는다.
- PSI URL만 다르고 측정 시각·지표가 같으면 캐시 재사용 여부를 확인한다. 독립성 미확인 결과는 3회로 인정하지 않는다.
- 초기 HTML 보존, 홈 로딩/푸터 이동, 상세의 전체 DB·전체 번역 의존, 이미지 fallback, 다른 글 이동 중 이전 응답 노출, 광고 반복 작업을 확인한다.
- INP는 상호작용 실측 또는 현장 데이터가 있을 때만 판단한다. TBT를 INP로 대체하지 않는다. 현장 데이터가 없으면 실사용 CWV는 미검증이다.
- 목표·현재 예산은 PERFORMANCE.md를 따른다. 용량 감소를 페이지 가속률로 바꾸거나 단일 Lighthouse 점수를 전체 사이트 점수로 부르지 않는다.

## 5. 보안 엔지니어

- lockfile·npm audit·CI 원본을 확인한다. `npm audit --json`은 읽기 전용 진단이며 advisory와 실제 영향·패치 범위를 별도로 판단한다. 자동 `audit fix`, 패키지 갱신은 평가에 포함하지 않는다.
- 현재 Security Scan은 `npm audit --audit-level=critical`이다. 성공은 그 임계값의 검사 결과일 뿐 취약점 0개나 침투 테스트 통과가 아니다.
- `.env`·private/service-role 키의 client bundle 노출, 불필요한 로그·개인정보·토큰 노출을 확인한다. 발견값은 보고서에 원문 복사하지 않는다. 공개 가능한 설정키와 privileged secret을 구분한다.
- 실제 HTML/응답 헤더의 CSP, frame 제한, MIME, 캐시, 정상/없는 경로·redirect 처리를 비교한다. 헤더 존재만으로 XSS 방어 완료를 선언하지 않고 허용 범위·콘솔 위반·광고 호환도 확인한다.
- 인증·개인정보 응답은 성능을 위해 공개 공유 캐시나 immutable로 바꾸지 않는다. 로그아웃·계정 전환 후 다른 사용자의 데이터가 노출되지 않는지도 승인된 테스트 환경에서 검증한다.
- 입력·Markdown/HTML 렌더링의 sanitizer와 위험 URL 처리를 코드/회귀 테스트로 확인한다. 공격 payload는 별도 승인된 로컬/테스트 환경에서만 사용한다.
- 관리자 화면 숨김과 서버 권한을 분리한다. 인증이 필요한 읽기 거부도 UI만 보지 않고 서버 응답으로 확인한다. 테스트 권한이나 계정이 없으면 인증 영역은 미검증이다.
- Supabase: 현재 공식 문서와 관련 스킬을 먼저 확인한다. 로컬 migration 존재와 운영 반영을 구분하고 실제 적용 grants·RLS·Storage·view/function 권한 및 Advisors를 읽기 전용으로 확인한다. 사용자 수정 가능 `user_metadata`를 권한 근거로 사용하지 않는지 검사한다. [공식 RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security).
- 쓰기 허용/거부 검증은 별도 승인된 테스트 환경·전용 A/B/관리자 계정·테스트 레코드로 한다. 일반 사용자 A가 B의 데이터/관리자 동작을 변경하지 못하는지 작업별로 확인한다. JWT 갱신 조건도 기록한다.
- 기본 평가에서 운영 DB/Storage 쓰기·삭제·권한 변경·사용자 메타데이터 변조·부하/침투 스캔은 금지한다. 운영 사용자 데이터나 인증정보를 취득할 권한도 추정하지 않는다.
- 운영 접근 불가, 저장소만 검사, 의존성 진단만 수행 등 검증 범위를 정확히 표시한다. 도구 실패·권한 부족은 안전하다는 증거가 아니다.

## 6. 디자인·UX 엔지니어

- DESIGN.md 및 [상태 체크리스트](../design-system/ux-principles.md)를 기준으로 실제 브라우저에서 검사한다. 새 디자인 취향을 기존 정책보다 우선하지 않는다.
- 제목·게임 정체성, 사이드바/헤더/섹션 번호, 컨테이너 여백, 정보 계층, 글꼴, 줄바꿈, 장비·스탯 카드 크기의 허브 간 일관성을 비교한다.
- 같은 화면·viewport·스크롤 위치의 전후 스크린샷을 남긴다. 첫 화면만이 아니라 중간 장비/스탯·이미지 전환·본문·푸터·모달을 확인한다.
- 실제 이미지 표시·크롭·비율·alt·fallback을 확인한다. 잘못된 속성·아이콘·수치·배치는 사용자 원본과 항목별로 대조한다. 이미지 요청 성공만으로 올바른 그림이라고 판단하지 않는다.
- 필터, 검색, 링크, 뒤로가기, 탭, mobile menu를 직접 조작한다. 터치/키보드에서 접근 가능한 이름·포커스 표시·조작 순서·모달 복귀·가림/잘림을 확인한다.
- 긴 이름·다국어·좁은 화면·확대·Loading/Empty/Error/Success/reduced-motion을 확인한다. 테스트 도구가 지원하지 않는 조건은 미검증으로 표시한다.
- 대비·키보드·접근성 자동 검사와 수동 검사를 나누고 DESIGN.md의 접근성 기준에 대조한다. Lighthouse 접근성 100도 전체 접근성 보장이 아니다.
- 접근성 항목에는 사용한 WCAG 버전·성공 기준 ID·W3C 원문 링크·검사 방법을 기록한다. 측정하지 않은 항목까지 전체 적합 판정을 확대하지 않는다.
- 실제 브라우저의 console 오류·깨진 이미지·404를 증거로 남기고, 사이트 오류와 서드파티 경고를 구분한다. 정적 소스 검색으로 '콘솔 오류 0개'를 선언하지 않는다.
- overflow-x-hidden으로 잘림이 가려질 수 있으므로 scrollWidth만으로 합격시키지 않고 실제 요소 경계·스크린샷을 확인한다. 지연 이미지까지 스크롤하며 정상 fallback으로 원본 이미지 누락을 숨기지 않는다.
- 저장·제보 성공 UI만 보지 말고 실제 서버 응답/저장을 확인한다. 데모 동작은 데모로 표시하고 허가 없는 운영 쓰기는 하지 않는다.

## 7. 판정과 완료 조건

항목 상태는 PASS(증거와 기준 충족), FAIL(재현한 위반), UNVERIFIED(미검증·환경/권한/표본 부족), N/A(비적용 사유 있음)만 사용한다. 빈 칸은 PASS가 아니다. 필수 항목 누락은 UNVERIFIED다.

- P0: 비밀 유출·무단 관리자 권한·데이터 훼손·사이트 전면 장애 등 즉시 대응. 평가 과정의 위험 작업은 중지하고 사용자에게 알린다.
- P1: 핵심 여정 차단·권한 우회 가능성·지속적 빈 화면/주요 데이터 누락 등 배포/작업 완료를 막는 중대 결함. 수정 후 해당 분야 재검사와 다른 두 분야 영향 검사를 거친다.
- P2: 부분 회귀·가독성·성능 예산/목표 위반 등 우선 개선. 실제 영향에 따라 P1로 상향할 수 있다.
- P3: 핵심 기능을 막지 않는 경미한 개선.

확정 결함과 위험 후보는 구분한다. 운영 재현 전인 SQL 위험 후보를 '운영 침해 확정'으로 쓰지 않는다. 알려진 문제를 새로운 평가에서 지우거나 점수 평균으로 상쇄하지 않는다.

전체 통과는 세 독립 보고서와 필수 증거가 모두 있고 P0/P1 실패·핵심 미검증이 없을 때만 가능하다. 제한된 범위 통과는 그 범위를 제목에 명시한다. 사용자 지시에 따라 공개하지 않는 내부 증거는 안전한 로컬 위치에 보관한다.

## 8. 산출물과 기준 갱신

- 독립 보고서: `docs/reports/YYYY-MM-DD-review-<commit>-performance.md`, `-security.md`, `-design.md`.
- 취합 보고서: `docs/reports/YYYY-MM-DD-review-<commit>.md`. 재실행은 식별자를 추가해 이전 보고서를 덮어쓰지 않는다.
- [양식](../templates/three-engineer-review.md)에 재현 절차·기대/실제·severity·상태·원자료·제약·다음 조치를 기록한다.
- 공개 Git에 올리기 전 secret·쿠키·개인정보·관리자 화면·공격에 바로 이용 가능한 민감 증거를 점검하고 비공개 보관한다. 공개 보고서에는 정제된 요약과 내부 증거 참조만 둔다.
- 기준 갱신 시 이전 baseline과 변경 이유를 보존한다. 실패를 지우려고 측정 경로·예산·광고·콘텐츠를 바꾸지 않는다.
- 코드/데이터 수정 후 검증·commit/push/배포는 AGENTS.md를 따른다. 평가만 요청받으면 코드 수정·commit/push는 금지다.
- 이번 문서 작성은 평가 체계 구축이다. 새 production 전체 성능·보안·디자인 평가를 완료했다는 뜻이 아니다.
