# Rira Game Hub 프로젝트 심층 분석 보고서 (Research)

## 1. 프로젝트 개요
본 프로젝트는 다수의 게임(현재 `붕괴: 스타레일(hsr-hub)` 및 `명조(ww-hub)`)의 데이터를 통합 관리하고 정보를 제공하는 웹 애플리케이션입니다. Vite 기반으로 추정되며, `react-i18next`를 사용하여 다국어 처리를 지원하고 있습니다.

## 2. 주요 파일 및 구조 분석

### 2.1. 다국어 처리 (i18n.ts & en.json)
- **동작 방식**: `import.meta.glob`을 사용하여 `common-hub` 내의 모든 `*_en.json` 파일을 Eager 모드로 불러와 하나로 자동 병합합니다.
- **장점**: 새로운 게임 데이터가 추가될 때 수동으로 import 할 필요 없이 폴더 구조만 맞추면 자동으로 번역이 적용되는 확장성 높은 구조입니다.
- **개선점**: 현재 캐릭터나 무기 데이터(`.ts` 파일) 내부에 한국어 문자열이 하드코딩되어 있습니다. 글로벌 확장을 위해서는 이 하드코딩된 문자열들을 `en.json` 및 `ko.json`의 키(key) 값으로 매핑하는 작업이 필요합니다.

### 2.2. 정적 데이터 관리 (Characters, Lightcones, Weapons, Echoes)
- **구조 특징**: 
  - 개별 아이템(무기, 에코 등)을 유형별 배열(예: `BROADBLADES`, `SWORDS`)로 선언한 후, 마지막에 전개 연산자(`...`)를 통해 하나의 거대한 배열(`WEAPON_DATA`, `ECHO_DATA`)로 병합하여 내보냅니다.
  - 캐릭터 데이터(`dan_heng_il.ts`, `phainon.ts`, `rappa.ts`)는 단일 객체 형태로 `export default` 되고 있습니다.
- **데이터 일관성**: `common-hub/types` 폴더 내의 공통 인터페이스(`LightCone`, `Character`, `WuwaWeapon`, `WuwaEcho`)를 상속받아 강력한 타입 추론을 적용하고 있습니다.

## 3. 코드 패턴 및 최적화 대상 (Optimization Opportunities)

### 3.1. 반복되는 구조의 모듈화 (함수 추출)
- **현상**: 데이터 파일 내에 스탯(`baseStats`), 스킬 설명, 레벨별 돌파 재료 등의 구조가 매우 반복적으로 나타났습니다.
- **최적화 진행 중**: `hsr-hub/data/dataFactory.ts`에 `createHsrBaseStats`, `createMaterial`, `createSkill` 등을 구축하여 기존 캐릭터(`luocha.ts`, `serval.ts`, `huohuo.ts` 등)의 하드코딩된 스탯, 재료, 스킬 객체를 완전히 압축 및 리팩토링 완료/진행 중.
  - **최신**: 신규 캐릭터 `dan_heng_permansor_terrae.ts`에 데이터 팩토리 및 다국어 키 적용 완료.

### 3.2. 대용량 파일 분리 및 로딩 최적화
- `echoes.ts`나 `weapons.ts`와 같이 수많은 배열 객체를 담은 파일은 애플리케이션의 번들 크기를 키울 수 있습니다.
- **해결책 (설계 완료)**: 각 아이템을 카테고리별(`.ts` 파일)로 분할 후 `index.ts`를 통해 병합 Export 하는 구조를 아키텍처 규칙으로 수립하였으며, 제공되는 즉시 적용 가능합니다.

### 3.3. 하드코딩된 텍스트의 국제화(i18n) 변환
- 현재 `skill.description` 등에 구체적인 수치와 텍스트가 함께 결합되어 있습니다.
**해결책**: 텍스트 포맷과 수치 배열을 분리하여 관리해야 합니다. `i18n`의 파라미터 주입 기능(Interpolation)을 활용하면 데이터 구조를 훨씬 깔끔하게 만들 수 있습니다.
- **진행 상황 (작업 중)**: HSR 캐릭터 데이터 다국어 처리는 순조롭게 진행 중입니다.
- **최근 완료**: 신규 캐릭터 `단항•등황`의 모든 텍스트 데이터를 다국어 키로 분리 완료. 또한, 방대했던 게임 내 모든 재료(소모품, 승급, 경험치, 행적, 공통 드랍 등)의 위키 API 기반 동적 추출 및 다국어 100% 매핑 파이프라인을 완벽히 구축했습니다. 마침표(`.`)로 인한 파싱 오류를 `{ keySeparator: false }` 옵션으로 원천 차단했습니다. 공통 컴포넌트인 `Home.tsx` 및 HSR 캐릭터 공략 가이드 내 하드코딩된 세팅/옵션 문자열(`1순위`, `계산 중` 등)을 `en.json`에 완벽 매핑 완료.

### 3.4. 게임별(HSR / WW) 데이터 및 구조 심층 분석
- **붕괴: 스타레일 (HSR)**: 
  - `skills`, `eidolons`, `specialTerms` 등 텍스트 비중이 매우 높아, 다국어 처리(i18n)로 분리하지 않으면 향후 유지보수가 기하급수적으로 어려워집니다.
- **명조 (WW)**: 
  - `Gallery.tsx` 코드를 분석한 결과, 무기(`WEAPON_DATA`)와 에코 속성(기류, 전도 등)이 HSR 로직과 공통 UI 로직에 섞여 처리되고 있습니다.
  - 명조 전용 데이터의 경우 UI 단에서 타입 캐스팅(`as any[]`)이 종종 발견되어 타입 안정성(Type Safety)이 떨어지는 취약점이 있습니다.

### 3.5. 아키텍처 규칙: HSR 및 WW 도메인 로직의 철저한 분리 (Strict Separation of Concerns)
- **원칙**: `hsr-hub`와 `ww-hub`의 비즈니스 로직과 데이터 생성 유틸리티는 절대 `common-hub`에 섞이지 않고 각각의 고유 폴더에 배치되어야 합니다.
- **적용 사례**: 공통 폴더인 `dataHelper.ts`에 존재하던 `createHsrBaseStats` 같은 게임 종속 로직을 제거하고, `hsr-hub/utils/dataFactory.ts`를 신설하여 철저히 분리했습니다.
- **UI 분할 완료**: 두 게임은 공통 UI 컴포넌트 구조를 공유해야 하므로, `Gallery.tsx` 및 `SearchModal.tsx` 내부에 남아있던 `if (gameId === 'hsr')` 같은 분기 처리를 완전히 제거하고 `SEARCH_CONFIG` 등 추상화된 설정(Config) 주입 방식 및 전략 패턴(Strategy Pattern)으로 리팩토링을 완료했습니다.
- **모듈 경로 최적화**: `dataFactory.ts`를 도메인 내부 최적의 위치인 `hsr-hub/data/` 내부로 이관하여 모듈 해석 지연(TS 2307)을 원천 해결하고 깔끔한 참조(`../dataFactory`) 체계를 구축했습니다.
- **UI 아키텍처**: 비대해진 `Gallery.tsx`를 Atomic 디자인 패턴에 따라 `components/cards` 및 `components/modals`로 분할 완료하여 코드 라인 수를 크게 줄이고 가독성을 높였습니다. `tsconfig.json`의 `paths` 설정을 통해 `@` 경로 별칭이 작동하도록 구성하여 모듈 해석 안정성을 확보했습니다. (Vite 및 IDE의 완벽한 Alias 호환을 위해 `"baseUrl": "."` 필수 유지 및 TS 6.0 Deprecation 경고 무시 처리 `"ignoreDeprecations": "6.0"` 적용 완료).

### 3.7. 문서 통합 관리 및 로컬라이징 (Documentation & Localization)
- **문서 구조화**: 루트 디렉토리에 분산되어 있던 모든 `.md` 파일을 `docs/` 폴더 하위의 `analysis`, `reports`, `plans`, `tiers`로 재분류하여 관리 효율성을 극대화했습니다.
- **한글화 표준**: 프로젝트 내의 모든 기술 문서를 한국어로 번역하고, 각 문서 상단에 `문서 용도`를 명시하여 접근성을 개선했습니다.
- **티어표 가이드**: 신규 캐릭터 추가 및 등급 조정을 위한 표준 템플릿과 요약 문서를 구축하여 데이터 무결성을 확보했습니다.

### 3.8. 기술 부채(Technical Debt) 관리 및 번들 최적화
- **청산 완료**: 모듈 참조 끊김 현상을 방어하기 위해 임시로 만들었던 `MATERIAL_DETAILS` 브릿지 객체 삭제 및 단일 파이프라인(SSOT) 구축으로 메모리 누수 해결 완료.
- **데이터 표준화 진행**: 애쉬베일 등 최신 캐릭터 데이터의 팩토리 패턴 및 i18n 적용을 순차적으로 진행 중입니다.

## 4. 향후 개발 원칙 (Ground Rules)
1. **사전 검토**: 변수나 함수 추가 시 기존 모듈과의 중복 여부를 우선 확인.
2. **주석 필수**: 복잡한 데이터 구조나 배열 병합 로직, 특히 유틸리티 함수 위에는 JSDoc 형태의 상세 주석을 기입하여 유지보수성 확보.
3. **관심사 분리**: 데이터 선언, 비즈니스 로직(함수), UI 렌더링을 명확히 분리하여 배치.
4. **UI 모듈화**: 하나의 파일(컴포넌트)은 하나의 역할만 하도록 지속적으로 분할(Atomic Design 지향).
5. **도메인 분리 강화**: HSR 관련 파일은 `hsr-hub`, WW 관련 파일은 `ww-hub` 하위 폴더에서만 생성, 처리하며 공통 UI는 이를 Props나 Config로 주입받도록 설계.
