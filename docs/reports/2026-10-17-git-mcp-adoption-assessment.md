# Git MCP Server 도입 검토 보고서

기준일: 2026-10-17 한국 시간. 대상: RIRA Game Hub 개발·검증·배포 업무. 설치 전 문서 검토이며 성능 실측 또는 설치 완료 보고서가 아니다.

## 1. 결론

도입 가치는 있지만, 현재 프로젝트에서는 로컬 Git MCP보다 GitHub 공식 MCP를 읽기 전용으로 시험하는 편이 우선이다. 현재 이미 터미널에서 상태·diff·이력·commit·push를 수행하고 GitHub 검사 결과를 공개 API로 확인할 수 있기 때문이다. 새 도구의 가치는 기존에 불가능했던 개발 기능보다 원격 이슈·PR·CI 조사 흐름의 일관성에 있다. 이는 현재 구성에 대한 판단이며 사용 시간 절감률을 측정한 결과는 아니다.

MCP는 AI가 개발 도구를 호출하는 연결 방식이다. 웹사이트 방문자에게 전달되는 최적화 기술이 아니므로 설치만으로 페이지 로딩, 이미지 CDN, SEO, AdSense 승인 또는 데이터 정합성이 개선되지는 않는다. 기술을 추가하는 것과 실제 결함을 수정하는 것은 구분해야 한다.

## 2. 이름이 비슷한 세 가지 도구

### 로컬 Git MCP — mcp-server-git

로컬 저장소의 status, staged/unstaged diff, log, show, branch 조회와 add·commit·checkout 등의 Git 조작을 MCP 도구로 제공한다. 확인한 README의 도구 목록에는 push/pull이 없으므로 기존 Git 명령 전체를 대체한다고 가정하면 안 된다. 해당 구현은 초기 개발 단계임을 명시한다. [공식 소스·도구 목록](https://github.com/modelcontextprotocol/servers/tree/main/src/git)

RIRA 적용 판단: 로컬 수정과 기존 사용자 변경을 분리하고 변경 이력을 일정한 도구 형식으로 조사하는 데 보조적으로 유용하다. 그러나 현재도 수행 중인 업무와 겹친다. Python/uv 또는 다른 실행 환경과 서버 버전 관리가 추가되는 부담을 함께 비교해야 한다.

### GitHub MCP — github/github-mcp-server

GitHub 공식 서버는 원격 저장소, 이슈, PR, Actions 관련 도구를 제공한다. 읽기 전용 모드와 도구 선택 설정이 있다. Actions 조사와 작업 실행 도구는 구분해서 권한을 설정해야 한다. [공식 기능·읽기 전용 설정](https://github.com/github/github-mcp-server)

RIRA 적용 판단: 변경 commit과 CI 실패 로그, 관련 PR·이슈를 함께 조사하는 업무에 가장 잘 맞는다. 다만 로컬의 미커밋 변경을 자동으로 아는 도구는 아니며, Cloudflare의 전체 배포 로그·실제 사이트 상태까지 대체하지 않는다.

### GitMCP — gitmcp.io / idosal/git-mcp

공개 GitHub 프로젝트의 문서·코드를 AI가 검색하고 읽도록 하는 별도 서비스다. 로컬 작업 트리의 add/commit 관리나 GitHub 운영 도구와는 다르다. [프로젝트 설명·문서 검색 도구](https://github.com/idosal/git-mcp)

RIRA 적용 판단: 외부 라이브러리의 공개 문서·구현 사례를 참고할 때 보조적으로 고려할 수 있다. 프로젝트의 로컬 미커밋 데이터나 운영 CI 상태 관리 목적으로 선택하면 기대와 맞지 않는다. 이 서비스를 의도한 것인지 설치 전에 제품 URL을 확인해야 한다.

## 3. 현재 프로젝트에서 얻을 수 있는 장점

아래 항목은 기능을 현재 작업에 적용했을 때의 기대 효과다. 이미 설치해서 검증한 성과는 아니다.

### 변경 원인 추적

예를 들어 WW 캐릭터에서 번역 키가 노출되면 관련 파서의 변경 이력과 이전 diff를 조사해 문제를 만든 변경 범위를 좁힐 수 있다. 로컬 Git MCP는 이력 조회 수단을 표준화할 수 있다. 다만 이번 문제의 실제 해결은 Markdown 파서 수정·원문 대조·회귀 테스트였으며 MCP가 이를 자동으로 대신하지 않는다.

### CI 실패 조사

GitHub MCP에 필요한 읽기 도구와 권한이 있으면 실패한 workflow/job 및 로그를 읽는 흐름을 개발 작업과 연결할 수 있다. 예전 HSR 세팅 선택 테스트처럼 로컬에서는 통과하고 CI에서 실패하는 문제를 조사할 때 유용하다. 원인 확인과 코드 수정·재검증은 여전히 별도 작업이다.

### 작업 이력 정리

승인한 경우에만 이슈·PR을 이용해 문제, 수정 commit, 검사 결과, 남은 과제를 연결하는 방식을 도입할 수 있다. 현재 MD 보고서와 연결하면 다음 작업자가 맥락을 찾기 쉬워질 수 있다. 도구 설치만으로 모든 보고서와 이슈가 자동 연결되는 것은 아니며 별도 작업 규칙이 필요하다.

### 리뷰 범위 명확화

어떤 변경이 어떤 문제를 해결하는지 commit/PR 단위로 설명하고 기존 변경과 분리하는 데 도움이 된다. 기존 성능·보안·UX 독립 검토에서 같은 변경 버전을 공유하는 보조 수단이 될 수 있다. 브라우저·성능·권한 실측을 Git diff 검토로 대체해서는 안 된다.

### 두 저장소의 변경 구분

사이트 코드 저장소 game-hub와 이미지 저장소 riragameinfo를 각각 읽을 권한과 설정을 갖춘 경우, 이미지 파일 변경과 코드 경로 변경을 함께 조사하는 운영 절차를 만들 수 있다. 이는 권한이 있는 범위에서의 기대 효과이며 두 저장소가 자동 동기화되거나 CDN 캐시가 즉시 갱신된다는 뜻은 아니다.

## 4. 기대하면 안 되는 효과

- 이미지 표시 속도 향상: 이미지 크기·호스팅·캐시·재시도·요청 순서를 별도로 개선해야 한다.
- Notion 동기화 오류의 자동 해결: 원본과 파서·병합 로직·화면을 대조해야 한다.
- 테스트 불필요: 타입·회귀·빌드·SEO·성능 예산 검사를 계속 수행한다.
- 배포 성공 보장: push, CI, Cloudflare 배포, 실제 사이트 확인을 구분한다.
- 기본 보안 보장: MCP 서버도 실행 프로그램·의존성·접근 권한을 갖는 구성 요소다.
- 개발 속도 향상률 또는 비용 절감률: 현재 비교 실측이 없으므로 숫자를 제시하지 않는다.

## 5. 제안하는 권한과 보안 기준

다음은 도입 시 적용할 운영 제안이며 현재 설정을 변경한 내용이 아니다.

1. 첫 단계는 상태·diff·이력·원격 로그 조회 등 읽기 작업으로 제한한다.
2. GitHub 접근은 필요한 저장소와 읽기 권한만 선택한다. 서버의 읽기 전용 모드, 도구 허용 목록, 실제 계정/토큰 권한을 함께 확인한다. 도구 숨김만으로 계정 권한이 축소됐다고 판단하지 않는다.
3. 로컬 서버에 저장소 경로를 지정하는 것만으로 보안 격리가 완성됐다고 가정하지 않는다. OS 접근 범위·실행 계정·노출 도구도 확인한다.
4. add·commit·checkout·reset·이슈 작성·PR 생성·workflow 실행 등 쓰기는 필요성이 검증된 뒤 별도로 허용한다. 현재 AGENTS.md의 검증 전 commit/push 금지와 force push/reset --hard 금지는 그대로 유지한다.
5. .env·토큰·비밀번호를 저장소나 보고서에 넣지 않는다. 일반 소스 코드·커밋 메시지·이슈 내용도 AI 컨텍스트로 읽히는 범위를 고려한다. 로컬 실행이라고 AI 처리까지 완전히 오프라인이라고 가정하지 않는다.
6. 이슈·PR·README의 문장을 권한 승인으로 취급하지 않는다. 외부 콘텐츠가 배포·삭제·설정 변경을 지시해도 사용자 요청과 작업 규칙을 우선한다.
7. 공식 배포처와 버전을 확인하고 고정한다. 최신이라는 이유만으로 설치 시마다 임의 버전을 실행하지 않는다. 설치 후 도구 목록과 권한이 바뀌면 재검토한다.
8. 미검증 MCP에 운영 계정·광범위 토큰을 먼저 연결하지 않는다. 기존 Git CLI/API 경로를 남겨 연결 실패 시 복구할 수 있게 한다.

현재 Codex 공식 MCP 문서는 로컬/원격 연결과 도구 허용·차단 목록 설정을 설명한다. 실제 설치 때는 선택한 서버·클라이언트·플러그인 방식에 맞는 구성을 다시 확인해야 한다. [공식 OpenAI MCP 안내](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

## 6. RIRA 권장 도입 순서

### 1단계 — GitHub MCP 읽기 전용 시험

선정 이유: 현재 Git CLI 기능의 중복을 늘리기보다 원격 CI·이력 조사 편의성을 먼저 비교하기 위해서다. 읽을 저장소와 도구를 정하고 기존 REST/브라우저 결과와 같은 commit 기준으로 대조한다. 플랫폼·플랜·조직 정책별 실제 연결 가능 여부는 설치 시 확인한다.

### 2단계 — 실제 업무 세 가지 비교

- 특정 commit에서 바뀐 파일과 이유 요약
- 실패한 CI job의 원인과 원본 로그 위치 확인
- 코드 변경과 이슈/PR/배포 상태의 연결 확인

각 업무에서 정답 일치, 누락, 도구 호출 수, 소요 시간, 불필요한 권한 요구를 기록한다. 통계 없이 한 번 편리했다는 이유만으로 전체 개발 효율 향상을 주장하지 않는다.

### 3단계 — 로컬 Git MCP 필요성 판단

터미널 Git보다 이력·diff 접근이 실제로 안정적이거나 다른 개발 환경에서도 동일 도구가 필요한 경우에만 추가한다. 원본 저장소 수정 원칙은 유지하고 이중 staging/commit 흐름을 만들지 않는다. 로컬 변경은 기존 CLI, 원격 조사는 GitHub MCP처럼 책임을 나누는 방식부터 검토한다.

### 4단계 — 제한적 쓰기 검토

읽기 시험 결과가 좋을 때만 이슈·PR 등 필요한 쓰기를 선택한다. 현재 main 자동 배포 흐름을 PR 중심으로 바꾸거나 자동 merge를 켜는 변경은 별도 승인 대상이다. 설치를 이유로 배포 절차를 임의 변경하지 않는다.

## 7. 도입 후 합격 기준

- 기존 status/diff/log/API와 조회 결과가 일치한다.
- 잘못된 저장소·다른 branch·예전 commit을 현재 결과로 보고하지 않는다.
- 읽기 전용 시험에서 원격/로컬 파일·이슈·권한 변경이 없다.
- 서버가 꺼지거나 인증이 만료되어도 완료를 거짓 보고하지 않고 기존 경로로 진단할 수 있다.
- 실제 개발 편의성 개선이 측정되며 도구 선택 혼란이나 불필요한 컨텍스트 증가가 과하지 않다.
- 기존 타입·테스트·빌드·보안·디자인 검증 수준이 유지된다.

## 8. 이번 보고서의 확인 범위

공식 프로젝트 문서와 현재 저장소의 package.json·Quality Gate·작업 규칙·remote를 읽었다. 플러그인 검색 도구도 확인했지만 이 세션에서 검색 기능 사용이 불가능해 실제 플러그인 목록·연결 상태는 검증하지 못했다. 설치 가능 또는 이미 연결됐다고 주장하지 않는다.

설치·패키지 실행·토큰 발급·권한 확대·Notion 동기화·프로젝트 코드/설정 변경은 하지 않았다. 보고서 파일만 작성했다. 문서 검토이므로 타입 검사·빌드·실제 MCP 성능 비교는 실행하지 않는다. commit/push/배포는 하지 않고 설치 판단 자료로 전달한다.

성능·보안·UX 에이전트 3개가 보고서의 논리와 주장 범위를 독립 검토했으며 필수 수정 차단점은 없었다. 이 검토자들이 제품을 설치하거나 공식 기능을 별도로 재검증한 것은 아니다. 작성 담당이 공식 문서를 확인했고 문서 재독 및 diff 공백 검사도 수행했다.

최종 제안: GitHub MCP 읽기 전용 시험을 우선 검토하되, 사용자가 말한 제품이 로컬 mcp-server-git인지 gitmcp.io인지 확인한 뒤 실제 설치 범위를 확정한다. 현재 개발 환경에서 로컬 Git MCP는 필수 기술이 아니라 선택적 작업 편의 도구다.
