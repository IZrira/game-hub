# 콘텐츠 관리자 권한 UX 호환 검토

2026-10-16. 별도 검토 에이전트가 기존 관리자 UI와 `20261016141014_restrict_content_writes_and_internal_function.sql`을 읽기 전용으로 대조했다. SQL 구현 담당과 구분되는 정적 검토이며, 실제 관리자 UI 종단간 검증은 아니다.

## 직접 확인한 범위

- `AdminDashboard.tsx`는 기존 두 `ADMIN_IDS`에 관리자 UI를 제공한다. 캐릭터 INSERT·UPDATE·DELETE, 공지 CRUD·일괄 UPDATE, 티어 INSERT/UPDATE UPSERT·DELETE를 사용한다.
- 후보는 세 테이블의 별도 SELECT 정책을 보존하고 모든 쓰기/ALL 정책을 관리자 INSERT·UPDATE·DELETE 정책으로 교체한다. 두 기존 관리자 UID 또는 서버 관리 `app_metadata.role=admin`을 허용하며 UPDATE는 USING과 WITH CHECK를 모두 가진다.
- 프론트와 관련 스크립트에서 `rls_auto_enable` 또는 RPC 호출은 발견되지 않았다. 후보는 해당 함수의 정의·이벤트 연결을 변경하지 않는다.
- 부계정의 캐릭터 삭제 권한 확대는 적용 전 별도 승인이 필요한 항목으로 전달했다. 주 담당은 이후 사용자 명시 승인을 받았다고 전달했다.

## 주 담당에게 전달받은 검증

운영 반영 후 SELECT 정책 6개, 기존 grants·RLS, 두 관리자 상태가 유지되고 관리자 쓰기 정책 9개가 확인되었다. 이벤트 함수 정의·바인딩은 유지되고 anon/authenticated EXECUTE는 차단, service_role EXECUTE는 보존되었다. Advisor는 12개에서 4개로 감소했으며 오류는 0개라고 전달받았다. 임시 clone 검사 90개와 애플리케이션 테스트 364개도 주 담당 실행 결과이며, 이 검토자가 독립 실행한 결과는 아니다.

## 독립 결론 및 UX → 보안 교차 검토

정적 대조상 기존 두 관리자의 정상 콘텐츠 관리 경로를 차단하는 변경은 발견하지 못했다. 공개 조회를 유지하면서 일반 사용자 쓰기를 제한하는 경계가 UI의 관리자 전용 의도와 일치한다. 다만 실제 관리자 로그인 세션에서 작성·수정·삭제·티어 저장을 수행한 종단간 검증은 미실시이므로 운영 UX 전체 통과로 표현하지 않는다.

기존 일부 관리 작업은 Supabase 반환 오류를 충분히 처리하지 않으므로 화면상 성공만으로 DB 반영을 판단하면 안 된다. 이는 이번 정책 변경의 정적 충돌과 구분되는 후속 개선이며, 실제 검증에서는 저장 후 DB 재조회가 필요하다. 본 검토자는 프로젝트 코드·SQL·운영 DB·브라우저를 변경하지 않았고 이 보고서만 작성했다.
