> **문서 용도**: 운영 배포 횟수를 줄이는 방법을 비교하고 추천안을 정한다. 근거 수치와 적용 순서를 담는다. 적용은 사용자 결정 뒤에 하고, Cloudflare 설정 변경과 `AGENTS.md` 규칙 변경은 사용자 승인이 필요하다.

# 배포 횟수 줄이기

- 작성일: 2026-11-09
- 배경: Search Console이 정상 페이지를 Soft 404로 판정했다(`docs/plans/search-recovery.md` R7). Google이 HTML을 받은 뒤 렌더링하기 전에 새 배포가 나가면, 이전 JS 파일이 사라져 오류 화면이 렌더링됐을 가능성이 크다. R7에서 이전 배포의 JS를 7일 동안 유지하도록 고쳤으므로, 배포를 줄이는 것은 보조 대책이다. 다만 배포가 잦으면 다른 비용도 생긴다(아래 "배포마다 생기는 일").

## 1. 현재 상태

### 수치(2026-10-26~11-09, Cloudflare Pages API와 Git 기록)

- 운영 배포: 68회(성공 67, 실패 1). 하루 최대 15회(11/8), 11/2~11/9 평균 하루 7회.
- 커밋: 67개. 이 중 9개(13%)는 `docs/`만 바꾼 커밋이다. 사이트에 아무 영향이 없는데도 운영 배포가 나갔다.
- 빌드 시간: 중앙값 82초, 최대 265초.
- 배포 방식
  - Cloudflare Pages Git 연동: `main`에 push하면 운영 배포가 나간다.
  - 다른 브랜치 push도 미리보기 배포가 나간다(`preview_deployment_setting: all`).
  - 빌드 감시 경로: 제외 경로 없음(`path_excludes: []`). 문서만 바뀌어도 빌드한다.
- 작업 규칙: `AGENTS.md` "Git 자동 처리"가 작업 하나가 끝날 때마다 push까지 하라고 정한다. 그래서 대화 한 번에 배포가 한 번씩 나간다.

### 배포마다 생기는 일

- JS 파일 이름이 바뀐다. 이전 HTML을 가진 방문자와 Google 렌더러는 이전 파일이 필요하다. R7 이후로는 7일 동안 유지된다.
- **IndexNow에 사이트맵 URL 792개 전체를 보낸다.** `scripts/generate-sitemap.js`의 `submitToIndexNow`는 Cloudflare 빌드(`CF_PAGES=1`)와 GitHub Actions(`GITHUB_ACTIONS=true`)에서 모두 실행된다. 그래서 push 한 번에 전체 목록이 두 번 나간다. 바뀌지 않은 URL까지 매번 보내면 Bing·네이버가 신호를 가볍게 볼 수 있다. IndexNow는 바뀐 URL만 보내도록 권장한다. 이번 검토에서 함께 고칠 항목으로 본다.
- Cloudflare 빌드 횟수를 쓴다. 무료 요금제의 월 빌드 한도(500회로 알려져 있음, 현재 요금제와 함께 확인 필요)를 지금 속도로는 넘지 않는다. 미리보기 배포를 늘리는 방식에서는 따져 봐야 한다.

## 2. 대안

### A. 빌드 감시 경로에서 문서 제외 (Cloudflare 설정)

- 방법: Pages 설정 "Build watch paths"의 제외 경로에 사이트 빌드와 관계없는 경로를 넣는다. 예: `docs/*`, `tests/*`, `.github/*`, `.agents/*`, `10_Wiki/*`, `20_Meta/*`, `_company/*`, `*.md`. push에 바뀐 파일이 모두 제외 경로에 있으면 빌드하지 않는다.
- 효과: 최근 2주 기준 커밋 13%가 배포 없이 끝난다.
- 장점: 설정 한 번이면 되고, 작업 규칙은 그대로다.
- 단점: 코드가 바뀌는 작업은 줄지 않는다. 빌드가 읽는 문서가 생기면 제외 목록을 고쳐야 한다. 지금은 빌드가 `.md` 파일을 읽지 않는 것을 확인했다(`hsr-hub/data/lightcones/*.md`는 메모 파일).
- 비슷한 방법: 커밋 메시지에 `[CF-Pages-Skip]`을 넣으면 그 push는 빌드하지 않는다. 사람이 매번 기억해야 해서 A보다 약하다.

### B. 작업 브랜치에서 모았다가 하루 1~2번 `main`에 반영 (추천)

- 방법
  - 평소 작업은 `dev` 브랜치에 commit·push한다. GitHub에 바로 올라가므로 백업과 CI(Quality Gate)는 지금처럼 매번 된다. Cloudflare는 미리보기 배포(`dev.rira-game-hub.pages.dev`)만 만들고 운영 사이트는 그대로다.
  - 하루 1~2번, 또는 사용자가 "배포해"라고 할 때 `dev`를 `main`에 fast-forward로 반영하고 push한다. 이때 운영 배포가 한 번 나간다.
  - 급한 수정(사이트 오류, 잘못된 정보)은 바로 `main`에 반영할 수 있다.
- 효과: 운영 배포가 하루 평균 7회에서 1~2회로 준다.
- 장점
  - 반영 전에 미리보기 주소로 실제 화면을 확인할 수 있다.
  - 작업이 GitHub에 남으므로 PC 문제로 작업을 잃을 걱정이 없다.
  - 되돌리기 쉽다(규칙만 원래대로 돌리면 된다).
- 단점과 대응
  - `AGENTS.md` "Git 자동 처리" 규칙을 바꿔야 한다. 작업 완료 때는 `dev`에 push하고, 운영 배포 확인은 `main`에 반영할 때만 한다.
  - 미리보기 빌드는 push마다 그대로 나간다. Cloudflare 설정을 `dev` 브랜치만 미리보기하도록 좁힌다. 빌드 한도를 확인한다.
  - 미리보기 빌드에서 IndexNow가 운영 URL을 제출하면 안 된다. 지금 코드는 `CF_PAGES=1`이면 브랜치와 상관없이 제출하므로, 운영 브랜치에서만 제출하도록 고쳐야 한다(아래 C).
  - CI는 지금 `main` push에서만 돈다. `dev` push에서도 돌도록 `quality-gate.yml`의 브랜치 조건을 넓힌다.
  - 미리보기 주소는 검색에 노출되면 안 된다. `pages.dev` 주소는 미들웨어가 본 도메인으로 301 이동하는데, 이때 브랜치 미리보기 주소(`dev.rira-game-hub.pages.dev`)는 대상이 아니다. 미리보기 응답에 `X-Robots-Tag: noindex`를 붙이는 처리가 필요하다.

### C. IndexNow는 운영 빌드에서 바뀐 URL만 제출 (B와 함께, 단독으로도 권장)

- 방법: `submitToIndexNow`를 Cloudflare 운영 빌드(`CF_PAGES_BRANCH=main`)에서만 실행한다. 라이브 사이트맵의 `lastmod`와 새 사이트맵을 비교해 새로 생기거나 날짜가 바뀐 URL만 보낸다. GitHub Actions와 미리보기 빌드에서는 보내지 않는다.
- 효과: push 한 번에 792개씩 두 번 보내던 것을, 실제로 바뀐 몇 개만 한 번 보내게 된다.
- 단점: 라이브 사이트맵을 읽지 못하면 이번 배포는 제출하지 않는다(다음 배포에서 함께 보냄).

### D. 운영 자동 배포를 끄고 정해진 시각에 배포

- 방법: Cloudflare에서 운영 자동 배포를 멈추고, GitHub Actions 예약 작업이 하루 1~2번 배포 훅을 호출한다. 바뀐 게 없으면 호출하지 않는다.
- 장점: 배포 시각이 일정하다.
- 단점
  - 급한 수정도 예약 시각까지 기다리거나 수동으로 배포해야 한다.
  - 배포 훅 주소를 GitHub 비밀값으로 관리해야 한다.
  - 지금의 "push 후 배포 확인" 절차와 맞지 않는다.
- B로 같은 효과를 더 단순하게 얻을 수 있어 추천하지 않는다.

### E. 지금처럼 매번 배포하고 push만 묶기

- 방법: `main`에 commit만 하고, push는 대화가 끝날 때나 여러 작업을 모아서 한다.
- 단점: push 전까지 작업이 이 PC에만 있다. CI도 늦게 돈다. 에이전트가 "push까지" 규칙을 지키는지에 기대게 된다. B가 이 단점 없이 같은 효과를 낸다.

## 3. 추천

1. **A + C를 먼저 적용한다.** 작업 규칙을 바꾸지 않고, 효과는 바로 난다.
   - A: Cloudflare 설정 변경(사용자 승인 후 에이전트가 API로 변경하거나 사용자가 대시보드에서 변경)
   - C: 코드 수정(`scripts/generate-sitemap.js`), 테스트 추가
2. **B는 사용자가 원하면 적용한다.** 운영 배포가 가장 많이 준다. 규칙 변경이라 사용자 결정이 필요하다.
   - `AGENTS.md` "Git 자동 처리"와 "작업 흐름"을 `dev` 기준으로 바꾸고, 운영 반영 절차("배포해")를 추가한다.
   - Cloudflare 미리보기 브랜치를 `dev`로 제한한다.
   - CI 브랜치 조건, 미리보기 noindex, IndexNow 운영 전용(C)을 함께 적용한다.
   - 운영 반영 주기(예: 하루 1회 저녁, 또는 요청 시에만)를 사용자가 정한다.
3. D와 E는 쓰지 않는다.

## 적용 기록

- 2026-11-09 사용자 결정: A·C 적용, B는 보류.
- C 적용(`fc27bd3`): `scripts/lib/indexnow.js`. 운영 Pages 빌드(`CF_PAGES_BRANCH=main`)에서만, 라이브 사이트맵과 비교해 새로 생기거나 `lastmod`가 바뀐 URL만 제출한다. 라이브 사이트맵을 읽지 못하면 제출하지 않는다. 배포 로그: "IndexNow: no new or changed URLs." `lastmod`가 없는 URL(광추, Notion 항목 등)은 내용이 바뀌어도 새 URL이 아니면 제출되지 않는다.
- A 적용(2026-11-10, 사용자가 대시보드에서 설정, 화면으로 값 확인): API 토큰에 Pages 편집 권한이 없어("Authentication error") 사용자가 직접 설정했다. 제외 경로: `docs/*`, `tests/*`, `.github/*`, `.agents/*`, `.claude/*`, `00_Raw/*`, `10_Wiki/*`, `20_Meta/*`, `40_*`, `_company/*`, `*.md`. 빌드는 이 경로의 파일을 읽지 않는다(2026-11-09 확인).
- Cloudflare 문서(Build watch paths, 2026-04-21 갱신) 기준: 제외 경로를 먼저 걸러 내고 남은 파일이 포함 경로에 맞으면 빌드한다. `*`는 `/`까지 포함해 하위 폴더를 모두 맞춘다. push에 변경 파일이 3,000개 이상이거나 커밋이 20개 이상이면 경로와 관계없이 빌드한다. 운영·미리보기 구분은 문서에 없다.

## 4. 결정이 필요한 것

- A 적용 여부와 방법(에이전트가 Cloudflare API로 변경 / 사용자가 대시보드에서 변경)
- C 적용 여부
- B 적용 여부와 운영 반영 주기

## 5. 확인하지 못한 것

- Cloudflare 요금제와 월 빌드 한도는 API로 확인하지 않았다.
- 빌드 감시 경로가 push에 포함된 모든 커밋의 파일을 기준으로 판단하는지, 마지막 커밋만 보는지는 공식 문서로 다시 확인한 뒤 적용한다.
- IndexNow 전체 재제출이 Bing·네이버 평가에 실제로 불이익을 주는지는 확인되지 않았다. 권장 방식과 다르다는 점만 근거로 했다.
